# 나의 Claude 개발 프로세스 적용 절차

> 「[나의 Claude 개발 프로세스](나의%20claude%20개발%20프로세스.md)」를 실제 개발 프로젝트에 적용하는 순서를 정리한 문서다. 프로세스의 원칙과 근거는 프로세스 문서에 있고, 이 문서는 무엇을 어떤 순서로 만들고, 무엇을 확인하면 다음 단계로 넘어가는지를 다룬다. "프로세스 6.2"처럼 적은 것은 프로세스 문서의 절을 가리킨다.

## 1. 적용 방식

### 1.1 스킬 하나로 만들지 않는 이유

프로세스의 핵심 원칙은 "규칙은 문장이 아니라 장치로 강제한다"(프로세스 2장)이다. 스킬은 Claude가 읽고 따르는 지시문이므로 "문장"에 속하고, 필요할 때만 불러오므로 실행된다는 보장도 없다. 그래서 야간 파이프라인의 승인 확인, 권한, 경로 검사는 스크립트와 설정 파일로 만든다. 스킬은 주간에 사용자와 함께 진행하는, 판단이 필요한 절차에만 쓴다.

### 1.2 구성 요소별 형식

| 구성 요소 | 형식 | 위치 | 변경 주체 |
|---|---|---|---|
| 원칙과 근거 | 문서 | 키트 저장소 `docs/` | 사용자 |
| 프로젝트 공통 규칙 | `CLAUDE.md` | 각 프로젝트 | 프로젝트 담당 |
| 야간 역할 정의 4개 | 에이전트 정의 | 키트 템플릿 → 각 프로젝트 `.claude/agents/` | 키트에서 고친 뒤 프로젝트에 반영 |
| 프로젝트별 설정 | `.claude/night.config.json` | 각 프로젝트 | 프로젝트 담당 (야간 에이전트는 수정 불가) |
| 문서 양식 | 템플릿 | 키트 → 각 프로젝트 `docs/`, `work/` | 키트 |
| 규칙 강제 장치 | 오케스트레이터·검사 스크립트, 역할별 권한·샌드박스·훅 | 키트 `night-ops/` → WSL `/opt/night-ops` | 키트 (설치는 `sudo`) |
| Windows 쪽 도구 | 승인 스크립트, 작업 스케줄러 등록 스크립트 | 키트 `windows/` → `%USERPROFILE%\night-ops\` | 키트 |
| 주간 절차 | 스킬 5개 | 키트 `skills/` → 개인 범위 설치, 이후 플러그인 | 키트 |

역할 정의는 모든 프로젝트에 같은 내용을 쓴다. 프로젝트마다 다른 내용(코딩 규칙, 빌드 방법, 검증 명령, 허용 경로, 상한값)은 `CLAUDE.md`와 프로젝트별 설정에 둔다. 그래야 키트를 고쳤을 때 모든 프로젝트에 같은 역할 정의를 다시 배포할 수 있다.

## 2. 적용 단계 개요

| 단계 | 목적 | 기간(예상) | 다음 단계로 넘어가는 기준 |
|---|---|---|---|
| 1. 시범 적용 | 프로젝트 하나에 수작업으로 적용하고, 운영하면서 절차를 다듬는다 | 2~3주 | 3.9의 완료 기준 |
| 2. 키트 추출 | 검증된 템플릿·스크립트·절차를 키트 저장소와 스킬로 만든다 | 1주 내외 | 4.4의 완료 기준 |
| 3. 확산 | 다른 프로젝트와 팀원에게 적용하고, 필요하면 플러그인으로 배포한다 | 필요할 때 | — |

1단계에서는 절차를 스킬로 굳히지 않는다. 시범 기간에는 양식과 절차가 자주 바뀌므로, 바뀔 때마다 스킬까지 고치면 비용만 늘어난다.

## 3. 1단계: 시범 적용

### 3.1 사전 확인

**시범 프로젝트 선정 기준**

- [ ] Linux에서 빌드·테스트된다 (프로세스 18.3)
- [ ] git 저장소다
- [ ] 자동 테스트가 있거나, 테스트 명령을 정할 수 있다
- [ ] 운영 영향이 작고 되돌리기 쉬운 작업이 있다
- [ ] 인터페이스를 설계문서로 확정할 수 있는 작업이 있다 (테스트 작성 에이전트 적용 대상)

**회사 정책**

- [ ] WSL에 Ubuntu 배포판을 추가로 설치할 수 있다
- [ ] 야간에 PC를 켜 둘 수 있다 (절전, 자동 업데이트 재시작 정책 확인)

**계정**

- [ ] 지금 쓰는 구독으로 진행한다 (프로세스 18.1)
- [ ] 사용량 기록 형식을 정했다 (프로세스 18.2)

### 3.2 야간 실행 환경 구성

프로세스 16.2의 순서를 따른다.

- [ ] Ubuntu 배포판을 설치하고 WSL2인지 확인했다 (`wsl -l -v`)
- [ ] `bubblewrap`, `socat`, `git`, `jq`와 프로젝트 빌드 도구를 설치했다
- [ ] 배포판 안에 Claude Code를 설치하고 로그인했다
- [ ] `/etc/wsl.conf`로 Windows 드라이브 마운트와 Windows 프로그램 실행을 끄고 배포판을 다시 시작했다
- [ ] 배포판에서 `/mnt/c`가 보이지 않고 `powershell.exe`를 실행할 수 없는 것을 확인했다

### 3.3 통제 폴더 구성

배포판 안에 `/opt/night-ops`를 만들고 다음 파일을 둔다. 배포판에서 Windows 드라이브가 보이지 않으므로, 1단계에서는 Windows 탐색기로 `\\wsl.localhost\night-ubuntu\home\<사용자>\`에 파일을 복사한 뒤 배포판 안에서 `sudo`로 옮긴다.

| 파일 | 하는 일 | 근거 |
|---|---|---|
| `run-night.sh` | 야간 단계를 순서대로 실행 | 프로세스 7장, 13.3 |
| `check-ready.sh` | 승인 해시, 상태, 프로젝트 설정 확인 | 프로세스 6.1, 6.3 |
| `check-paths.sh` | 단계 후 실제 변경 파일이 역할별 허용 경로 안에 있는지 검사 (프로젝트 설정의 허용 경로 사용) | 프로세스 11장 |
| `record-usage.sh` | 단계별 사용량을 `~/night-logs/usage.csv`에 누적 | 프로세스 18.2 |
| `hooks/guard.sh` | 금지 명령 차단과 차단 기록 | 프로세스 13.2 |
| `roles/*.json` | 역할별 권한·샌드박스·훅 (4개) | 프로세스 11장, 13.2 |
| `mcp-empty.json` | MCP 서버를 하나도 불러오지 않게 하는 빈 설정 | 프로세스 11장 |

- [ ] 위 파일을 만들었다
- [ ] 통제 폴더를 root 소유로 바꾸고 일반 사용자의 쓰기를 막았다 (`sudo chown -R root:root /opt/night-ops`, `sudo chmod -R go-w /opt/night-ops`)
- [ ] `~/night-logs`를 만들었다 (일반 사용자 쓰기 가능, 에이전트 읽기는 역할별 설정에서 차단)

### 3.4 프로젝트 준비 (Windows 작업 사본)

- [ ] `CLAUDE.md`: 공통 규칙(코딩 규칙, 빌드·테스트 방법, 금지 동작)만 적었다
- [ ] `.claude/settings.json`: 공통 거부 규칙과 `disableClaudeAiConnectors: true`를 넣었다
- [ ] `.claude/agents/`: 역할 정의 4개(`test-author`, `implementer`, `design-interpreter`, `reviewer`)를 만들었다 (프로세스 13.1)
- [ ] `.claude/night.config.json`: 프로젝트별 설정을 작성했다 (아래 예시)
- [ ] `docs/`: 요구사항, 아키텍처, 테스트 전략, `decisions/`, `design/current-design.md` 양식을 배치했다
- [ ] `work/`: `current-task.md` 양식(프로세스 6.1 항목), `status.json`(초기값 `planned`), `queries/open`, `queries/answered`, `reviews/`, `handoff/`를 만들었다
- [ ] `tests/unit/`, `tests/acceptance/`를 만들었다
- [ ] 위 내용을 커밋했다

프로젝트별 설정 예시는 다음과 같다. 작업 정의(`current-task.md`)에 실행 상한이 따로 적혀 있으면 오케스트레이터는 그 값을 우선한다.

```json
{
  "project": "order-service",
  "verify": {
    "test": "npm test",
    "lint": "npm run lint",
    "typecheck": "npm run typecheck",
    "build": "npm run build"
  },
  "allowedPaths": {
    "test-author": ["tests/acceptance/**"],
    "implementer": ["src/**", "tests/unit/**", "work/queries/open/**", "work/handoff/impl-notes.md"],
    "design-interpreter": ["work/queries/answered/**"],
    "reviewer": ["work/reviews/**"]
  },
  "limits": {
    "queryRounds": 2,
    "fixRounds": 1,
    "limitedDecisions": 5,
    "endTime": "06:00",
    "maxTurns": { "test-author": 60, "implementer": 200, "design-interpreter": 40, "reviewer": 80 },
    "maxBudgetUsd": { "test-author": 5, "implementer": 20, "design-interpreter": 3, "reviewer": 10 }
  }
}
```

이 파일은 `.claude/` 아래에 있으므로 야간 에이전트는 권한 규칙과 샌드박스 양쪽에서 수정이 막힌다. 에이전트가 자기 허용 경로나 상한을 바꿀 수 없다.

### 3.5 저장소 연결과 예약 실행

- [ ] 배포판 안에 bare 저장소를 만들었다 (`git init --bare ~/repos/<프로젝트>.git`)
- [ ] Windows 작업 사본에 원격을 등록했다 (`git remote add night //wsl.localhost/night-ubuntu/home/<사용자>/repos/<프로젝트>.git`). 소유자 확인 경고가 나오면 `safe.directory`에 등록했다
- [ ] 첫 push를 했다 (`git push night main`)
- [ ] 승인 스크립트(`approve.ps1`)를 만들었다: 형식 검사 → 해시 기록 → 커밋 → push (프로세스 6.3)
- [ ] 작업 스케줄러에 야간 작업을 등록했다 (프로세스 16.4). 리허설이 끝날 때까지는 비활성으로 둔다

### 3.6 첫 작업 준비

- [ ] 작은 작업을 골랐다: REQ 3개 이하, 변경 파일이 적고, 인터페이스가 확정된 작업
- [ ] 설계 리드 세션에서 설계문서와 작업 정의를 작성했다 (프로세스 6장)
- [ ] 설계 완성도 판정을 했다 (프로세스 6.2). 스킬이 아직 없으므로, 프로세스 6.2의 사전 질의 추출 지시를 읽기 전용 모드(`--permission-mode plan`)의 새 세션에 그대로 넣어 실행한다
- [ ] 승인 스크립트로 승인했다

### 3.7 주간 리허설

- [ ] 사용자가 자리에 있을 때 배포판에서 `run-night.sh`를 직접 실행했다
- [ ] 프로세스 17장의 리허설 점검 항목을 모두 확인하고, 결과를 키트 폴더의 `docs/리허설 기록.md`에 남겼다
- [ ] 문제가 나온 항목은 고친 뒤 그 항목만 다시 확인했다
- [ ] 모든 항목을 통과한 뒤 작업 스케줄러의 야간 작업을 활성화했다

### 3.8 소규모 야간 운영

하루 한 작업, 되돌리기 쉬운 범위로 2~3주 운영한다.

| 시점 | 할 일 | 근거 |
|---|---|---|
| 아침 | 야간 브랜치를 fetch해 결과보고서 검토, 사용자 결정, 병합 또는 재작업, 중단·실패 원인 분류 확인 | 프로세스 14장, 6.2 사후 보정 |
| 업무시간 | 다음 작업 설계와 설계 완성도 판정 | 프로세스 6장, 6.2 |
| 퇴근 전 | 승인 | 프로세스 6.3 |
| 야간 | 자동 실행 | 프로세스 7장 |

매주 다음을 한다.

- [ ] 사용량 기록을 검토했다 (프로세스 18.2)
- [ ] 원인 분류 중 "설계 누락" 유형을 설계 완성도 판정의 체크리스트나 시나리오 질문에 추가했다
- [ ] 템플릿·스크립트·역할 정의에 고친 내용을 변경 기록으로 남겼다

### 3.9 1단계 완료 기준

- 리허설 점검 항목을 모두 확인했다
- 야간 실행이 10건 이상 쌓였다 (사용량 측정 표본, 프로세스 18.2)
- 최근 1주 동안 환경·권한 문제로 인한 중단이 없었다
- 템플릿·스크립트·역할 정의가 1주 이상 바뀌지 않았다
- 설계 누락으로 인한 중단이 줄어드는 추세다

## 4. 2단계: 키트 추출

### 4.1 키트 저장소 구조

이 폴더(`DL Developer Model`)를 git 저장소로 만들어 키트 저장소로 쓴다.

```text
DL Developer Model/
├─ docs/
│  ├─ 나의 claude 개발 프로세스.md
│  ├─ 나의 claude 개발 프로세스 적용 절차.md
│  └─ 리허설 기록.md
├─ templates/project/             # 프로젝트에 복사할 파일
│  ├─ CLAUDE.md                   # 공통 규칙 뼈대
│  ├─ .claude/
│  │  ├─ settings.json
│  │  ├─ night.config.json        # 견본
│  │  └─ agents/                  # 역할 정의 4개
│  ├─ docs/                       # 설계문서·ADR 양식
│  └─ work/                       # 작업 정의·질의·보고서 양식, status.json 초기값
├─ night-ops/                     # WSL /opt/night-ops에 설치
│  ├─ install.sh
│  ├─ run-night.sh
│  ├─ check-ready.sh
│  ├─ check-paths.sh
│  ├─ record-usage.sh
│  ├─ hooks/guard.sh
│  ├─ roles/*.json
│  └─ mcp-empty.json
├─ windows/
│  ├─ approve.ps1
│  └─ register-task.ps1           # 작업 스케줄러 등록
└─ skills/
   ├─ night-init/
   ├─ night-design/
   ├─ night-readiness/            # 형식 검사 스크립트 포함
   ├─ night-approve/
   └─ night-review/
```

### 4.2 옮기는 순서

1. 시범 프로젝트에서 쓰던 파일을 위 구조로 옮긴다. 프로젝트마다 다른 값은 `night.config.json`과 `CLAUDE.md`로 분리한다.
2. `night-ops/install.sh`를 만든다. `/opt/night-ops`로 복사하고 root 소유와 권한을 설정한다. 배포판에서는 Windows 드라이브가 보이지 않으므로, 키트도 프로젝트처럼 배포판의 bare 저장소로 push하고 배포판 안에서 받아 `sudo ./install.sh`로 설치한다.
3. Windows 쪽 스크립트(`approve.ps1`, `register-task.ps1`)를 정리한다.
4. 스킬을 만든다(4.3).
5. 키트에 버전 태그를 붙인다. 결과보고서의 실행 정보에 키트 버전을 남겨, 어느 버전의 키트로 실행했는지 추적할 수 있게 한다.

### 4.3 스킬

| 스킬 | 하는 일 | 호출 | 근거 |
|---|---|---|---|
| `night-init` | 새 프로젝트에 템플릿 배치, 프로젝트별 설정 작성 안내, 배포판 bare 저장소와 원격 등록 | 사용자 | 3.4, 3.5 |
| `night-design` | 작업 정의를 착수 조건 양식대로 작성하고, 의사결정 항목을 네 가지로 분류하게 안내 | 사용자 또는 Claude | 프로세스 6장, 6.1 |
| `night-readiness` | 형식 검사 → 내용 체크리스트 → 읽기 전용 하위 에이전트로 사전 질의 추출 → 판정 출력 | 사용자 또는 Claude | 프로세스 6.2 |
| `night-approve` | 판정이 "착수 가능"일 때 승인 스크립트 실행 | 사용자만 | 프로세스 6.3 |
| `night-review` | 야간 브랜치 fetch, 보고서 요약, 사용자 결정 사항 정리, 병합·재작업 안내, 원인 분류 기록 | 사용자 또는 Claude | 프로세스 14장, 6.2 사후 보정 |

- 스킬은 절차를 진행하고, 판정과 기록은 스킬에 함께 넣은 스크립트가 한다(형식 검사, 해시 기록). 판정 기준이 스킬 지시문의 해석에 따라 흔들리지 않게 하기 위해서다.
- 승인은 사용자의 명시적인 행위이므로 `night-approve`는 Claude가 스스로 호출하지 못하게 설정한다.
- 스킬은 먼저 개인 범위(`%USERPROFILE%\.claude\skills\`)에 설치해 쓴다.

### 4.4 2단계 완료 기준

- 시범 프로젝트를 새로 받은 작업 사본에 키트만으로 다시 적용해도 1단계와 같은 결과가 나온다
- 키트로 처리하지 못하는 수작업이 남아 있다면, 그 단계가 체크리스트에 모두 적혀 있다

## 5. 3단계: 확산

### 5.1 새 프로젝트 적용 체크리스트

- [ ] 프로젝트가 Linux에서 빌드·테스트되고 git 저장소인지 확인했다
- [ ] `night-init`으로 템플릿을 배치했다
- [ ] `CLAUDE.md` 공통 규칙과 `.claude/night.config.json`을 작성했다
- [ ] 축약 리허설을 했다: 샌드박스 동작, 경로 검사로 인한 실행 중단, push·fetch, 작은 작업 1건
- [ ] 첫 작업은 작은 범위로 시작했다
- [ ] 첫 2주는 이 프로젝트의 사용량과 원인 분류를 따로 본다. 프로젝트마다 특성이 다르기 때문이다

### 5.2 한 PC에서 여러 프로젝트 운영

야간 실행은 한 번에 한 작업씩 한다(프로세스 5장). 프로젝트가 여럿이면 작업 스케줄러 작업 하나가 승인된 프로젝트를 정해진 순서로 하나씩 실행한다. 프로젝트별 종료 시각과 비용 상한의 합이 야간 시간과 사용량 한도 안에 들어오게 정한다.

### 5.3 플러그인 배포

두 번째 사람이 합류하거나 적용 프로젝트가 늘면, 스킬과 프로젝트 템플릿을 플러그인으로 묶어 사내 git 저장소로 배포한다.

- `night-ops`는 WSL에 root 소유로 설치하는 OS 수준 도구이므로 플러그인에 넣지 않는다.
- 플러그인에 넣은 에이전트는 권한 모드와 훅 설정이 무시된다. 이 프로세스는 역할별 설정 파일로 권한을 강제하므로 영향은 없다. 다만 야간 실행에서 `--agent`로 지정하는 동작은 프로젝트 `.claude/agents/`의 정의로 리허설한 것이므로, 역할 정의는 플러그인으로 옮기지 않고 프로젝트 템플릿으로 유지한다.

### 5.4 키트 변경 관리

- 프로세스가 바뀌면 프로세스 문서를 먼저 고치고 키트를 고친다.
- 키트 변경은 소유자 1명이 반영하고 버전을 올린다. 여러 명이 쓰게 되면 에이전트 운영 담당이 소유자가 된다.
- 프로젝트 반영: 역할 정의와 양식은 `night-init`으로 다시 배치하거나 직접 복사하고, 통제 폴더는 `install.sh`를 다시 실행한다.
- 키트를 바꾼 뒤 첫 야간 실행 전에는 축약 리허설로 확인한다.
